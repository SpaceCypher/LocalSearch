# LocalSearch vs Spotlight

Generated by `cargo run --release --example bench_vs_spotlight`. This is the fourth run, and the first with the on-disk index; see the notes at the end for what differed between runs.

## Setup

- Machine: Apple M3, 8 GB RAM
- macOS 26.3
- LocalSearch commit `636133c`, release build
- Scope for both: `~/Downloads`, `~/Documents`, `~/Desktop` (59658 items in the LocalSearch index)
- Both are called in-process: LocalSearch through `Engine::search`, Spotlight through `MDQueryExecute` (synchronous). No `mdfind` process start-up is included.
- Both are capped at 100 results per query.
- Each query: 3 warm-up runs, then up to 30 measured runs (fewer if the query used more than 20 s in total). Times are milliseconds.

## Time until a new file is findable

A file with a unique name is created in an indexed folder and both engines are polled every 10 ms until they return it.

- LocalSearch: 0.39 s (median of 5; range 0.37–0.78 s)
- Spotlight: not found within 30 s in 5 of 5 trials in this run. **Treat this as an outlier, not as typical.** Two earlier runs on the same machine measured 1.81 s and 1.95 s (medians of 5). A manual check (`mdfind` polling for a newly created file) confirmed Spotlight was not picking up new files on this machine after sustained build and test work; it appears to have been behind.

## Searching while the index is being saved

LocalSearch periodically merges recent changes into its on-disk index. One query (`report`) is repeated continuously on another thread before and during a merge.

- Before the save: median 12.0 ms, worst 15.8 ms (165 queries)
- During the save (0.5 s): median 14.2 ms, worst 20.2 ms (32 queries)

## LocalSearch resource cost

Spotlight's index is built and held by the system for every app, so there is no equivalent per-app figure to set beside these.

- First index, names only: 6.6 s for 59658 items (search is usable from here)
- First index, names and contents: 67.2 s in total
- Share of text, code, PDF and Word/RTF files whose contents were indexed: 100%
- Process memory right after the first index: 156 MB (includes memory the allocator has not yet returned)
- Process memory after loading the saved index in a fresh process: 112 MB
- Index on disk: 22 MB
- Loading the saved index on a later launch: 1.20 s for 59658 items

## What this does not show

- One machine, one set of files. Numbers will differ elsewhere.
- Spotlight indexes the whole machine and many more file types (Office documents, mail, images); LocalSearch here covers three folders and reads only text, code and PDF contents. Hit counts are therefore not a measure of which is more complete.
- Spotlight needs no index build by the user and no extra memory in the app.
- The typo queries are included because LocalSearch tolerates misspellings and Spotlight matches literally; zero Spotlight hits there is expected behaviour, not a failure.
- The engines do not interpret a query the same way. For several words LocalSearch returns files matching any of them (ranked by how many match); the Spotlight queries here require every word. LocalSearch also returns approximate matches, so its hit counts include loose ones.
- Result quality (whether the best file is ranked first) is not measured.
- Known anomaly, not shown above: in the first of the four runs of this benchmark, the first execution of one LocalSearch query (`license`) took about 10 s. It has not recurred in three later runs and the cause was never identified. Query timings are no longer written to disk on the query path, and any query slower than 250 ms is logged with a per-stage breakdown, so a recurrence can be diagnosed.
- Earlier runs used an index held entirely in memory. On the same files that design measured 374 MB of process memory after loading, a 49 MB save file and a 1.39 s load, against 112 MB, 22 MB and 1.20 s here. Query latency did not change materially.
