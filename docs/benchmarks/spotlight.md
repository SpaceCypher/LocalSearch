# LocalSearch vs Spotlight

Generated by `cargo run --release --example bench_vs_spotlight`. This is the third run; see the notes at the end for what differed between runs.

## Setup

- Machine: Apple M3, 8 GB RAM
- macOS 26.3
- LocalSearch commit `9478753`, release build
- Scope for both: `~/Downloads`, `~/Documents`, `~/Desktop` (59642 items in the LocalSearch index)
- Both are called in-process: LocalSearch through `Engine::search`, Spotlight through `MDQueryExecute` (synchronous). No `mdfind` process start-up is included.
- Both are capped at 100 results per query.
- Each query: 3 warm-up runs, then up to 30 measured runs (fewer if the query used more than 20 s in total). Times are milliseconds.

## Time until a new file is findable

A file with a unique name is created in an indexed folder and both engines are polled every 10 ms until they return it.

- LocalSearch: 0.35 s (median of 5; range 0.34–0.58 s)
- Spotlight: not found within 30 s in 5 of 5 trials in this run. **Treat this as an outlier, not as typical.** Two earlier runs on the same machine measured 1.81 s and 1.95 s (medians of 5). A manual check straight after this run (`mdfind` polling for a newly created file) confirmed Spotlight was not picking up new files at that moment; the machine had been doing sustained build and test work beforehand, and Spotlight appears to have been behind.

## Searching while the index is being saved

LocalSearch periodically writes its whole index to disk. One query (`report`) is repeated continuously on another thread before and during a save.

- Before the save: median 11.2 ms, worst 15.2 ms (176 queries)
- During the save (0.4 s): median 15.0 ms, worst 21.1 ms (27 queries)

## LocalSearch resource cost

Spotlight's index is built and held by the system for every app, so there is no equivalent per-app figure to set beside these.

- First index, names only: 4.3 s for 59642 items (search is usable from here)
- First index, names and contents: 59.5 s in total
- Share of text, code, PDF and Word/RTF files whose contents were indexed: 100%
- Process memory right after the first index: 540 MB
- Process memory after loading the saved index in a fresh process: 374 MB
- Index on disk: 49 MB
- Loading the saved index on a later launch: 1.39 s for 59642 items

## What this does not show

- One machine, one set of files. Numbers will differ elsewhere.
- Spotlight indexes the whole machine and many more file types (Office documents, mail, images); LocalSearch here covers three folders and reads only text, code and PDF contents. Hit counts are therefore not a measure of which is more complete.
- Spotlight needs no index build by the user and no extra memory in the app.
- The typo queries are included because LocalSearch tolerates misspellings and Spotlight matches literally; zero Spotlight hits there is expected behaviour, not a failure.
- The engines do not interpret a query the same way. For several words LocalSearch returns files matching any of them (ranked by how many match); the Spotlight queries here require every word. LocalSearch also returns approximate matches, so its hit counts include loose ones.
- Result quality (whether the best file is ranked first) is not measured.
- Known anomaly, not shown above: in the first of the three runs of this benchmark, the first execution of one LocalSearch query (`license`) took about 10 s. It has not recurred in two later runs and the cause was never identified. Saving the index was tested and ruled out. Since then, query timings are no longer written to disk on the query path, and any query slower than 250 ms is logged with a per-stage breakdown, so a recurrence can be diagnosed.
- The memory figures are for a fresh process that has just loaded the index and run one query. A long-running app has been observed lower (about 230 MB) once the allocator settles; that is a single observation, not part of this script.
